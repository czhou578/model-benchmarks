# Qwen3.6-35B-A3B NVFP4: Five-Config Batch Run (July 2026)

> **Correction (2026-11-09).** An audit compared this page with `resolved_server.json`, `model_config.yml`, and `summary.json` of each run dir. It found these errors:
>
> - Run 2 (`20260729_153414`) had no speculative decoding. Its server command has no `--speculative-config` flag, and it used `--moe-backend marlin`, not triton. The old page called it "nvidia + spec (MTP, k=3)" and said that spec decoding raised tool-calling accuracy from 31.8% to 38.8%. That claim is wrong. This page now calls run 2 "nvidia (no PC)". PC means prefix caching.
> - Only run 5 (unsloth + spec) used speculative decoding. No run pair changes only the spec setting.
> - The RedHat run used the managed `vllm serve` command of the harness, not Docker. It had `--enable-prefix-caching`. The Docker command is only a comment in its `model_config.yml`.
> - Run 5 used `--moe-backend flashinfer_cutlass`, not `flashinfer_b12x`.
> - Run 3 (RedHat) and run 5 sent 5 requests per concurrency level. Thus levels 8 and 16 had at most 5 requests in flight. Their flat throughput at levels 8 and 16 does not show saturation.
> - With MTP, one stream event carries several tokens. The decode peak and min values of run 5 count events, not tokens. Its 181.41 tok/s peak is not valid.
> - Runs 1, 3, and 5 had prefix caching on. Their TTFT values at 8192 tokens and more are mostly prefix-cache hits, not full prefills.
> - Some numbers did not match the run files. The tables now show the `summary.json` values. Run dir paths now use the current lowercase folder names.
> - The run dirs hold no `tool_calling.json`. Nobody can check the per-category pass counts and failure-mode counts on this page. `summary.json` holds only the totals and the composite components.
>
> With 85 tasks, the 95% confidence interval (CI) of one tool-calling pass rate is about ±10 points. The 95% CI of a difference between two runs is about ±14 points. The largest difference here is 13 points (35 vs 24 of 85). Thus no tool-calling difference on this page is significant.

This write-up covers five runs of Qwen3.6-35B-A3B NVFP4 on 2026-07-29 (era E0). `batch_run.py` generated the first version on 2026-07-30. These runs predate the tool-calling scorer fix and the cache-salt fix of 2026-11-07. They also sent one shared prompt to every concurrency request. Do not compare their TTFT, tool-calling, or concurrency numbers with newer runs. [../comparability.md](../comparability.md) describes the fixes and the comparability rules.

## Key Findings

### 1. Speculative Decoding: One Run Only

Only run 5 (unsloth + spec) used MTP spec decoding (k=3). The two nvidia runs had no spec decoding. Thus the data shows no spec effect for nvidia.
- **unsloth**: 35/85 without spec, 33/85 with spec. The difference is inside the noise.
- **unsloth + spec** has the **best mean decode speed**: 85.6 vs 74.9 tok/s (+14%).
- Runs 4 and 5 also differ in the MoE backend, prefix caching, the load format, the CUDA graph sizes, and the concurrency requests per level. Thus the +14% is not a clean spec effect.

The flat concurrency result of run 5 at levels 8 and 16 comes from its 5 requests per level. It does not show a spec decoding limit.

### 2. Unsloth Weights: Highest Tool-Calling Count, Inside the Noise

The unsloth (no spec) run passed the most tasks:
- **41.2% accuracy** (vs 31.8% nvidia, 28.2% RedHat)
- Best at: `currency_basic` (100%), `stock_basic` (100%), `weather_enum` (100%), `multi_tool` (43.75%)
- Lowest failure rate: 32 missing params, 18 wrong sequence

The per-category values and failure counts above are not in the run files. All differences are inside the noise (see the correction note). The run data does not show a cause.

### 3. RedHat Run Has About Half the Decode Speed

The RedHat run is slower in decode:
- Decode: mean 41.2 vs 74.9-85.6 tok/s in the other runs (about 50% less)
- Concurrency level 1: 40.5 vs 72.9-102.2 tok/s. Levels 8 and 16 are not comparable, because the run sent only 5 requests per level.
- Tool calling: 28.2% accuracy (lowest, but inside the noise)

**Possible causes**: The `RedHatAI` weights differ from the `unsloth` and `nvidia` weights. The run had no `--moe-backend` flag and no `--attention-backend` flag, so vLLM chose its defaults. The run data does not show which cause applies. The run had prefix caching on.

### 4. Prefix-Cache Hits in Long-Context TTFT

The nvidia (baseline) run reports **149,176 tok/s** prefill throughput at 64K context. Its median TTFT at 64K is 0.354 s, while run 2 needed 14.38 s. Run 1 had `--enable-prefix-caching`, and the harness then sent no cache salt in these benchmarks. Thus most repeats were prefix-cache hits. The RedHat and unsloth + spec runs show the same effect at 8192 and 16384 tokens.

### 5. RedHat Config Differences Matter

The RedHat model config differs from all others:
- Uses `RedHatAI/Qwen3.6-35B-A3B-NVFP4` source (not `unsloth` or `nvidia`)
- **No `--moe-backend` flag** (may use slow default)
- Prefix caching on (`--enable-prefix-caching`), as in runs 1 and 5
- The Docker image `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-tf5:latest` is only in a comment. The run did not use it.
- Only 5 concurrency requests per level (also in run 5; 16 in the other runs)
- `--max-num-batched-tokens=8192` (same as others)

### 6. Multi-Tool Orchestration Is the Hardest Benchmark

The pass counts below are not in the run files. Across ALL runs, multi-tool is the weakest category:
- unsloth: 43.75% pass rate (7/16) — best
- nvidia (no PC): 37.5% (6/16)
- nvidia: 18.75% (3/16) — worst

Yet data_flow_correct is consistently high (0.875-0.9375) — models understand the data flow, but struggle with the **orchestration** (tool sequencing and turn count).

### 7. Error Recovery Is Universally Poor

Error recovery passes at only 11.8%–29.4% across all runs (not in the run files). Models often don't retry when they get errors. The `error_no_retry` failure mode accounts for 12-15 errors per run.

### 8. Missing Parameters Are the #1 Failure

Across all runs, `missing_required_param` is the most common failure (32-47 occurrences, not in the run files), far exceeding wrong tool selection (0-2). This suggests the model struggles with parameter completeness rather than tool selection.

## Further Statistics

### 1. TTFT Tail Latency at Short Prompts

At 32 tokens, the **p99 TTFT is 3.5-8.6x the average** in four of the five runs. In the RedHat run, it is 1.07x. The worst case is the **unsloth (no spec)** run: at 32 tokens, the **median TTFT is 60ms but the p99 is 8.84s — a 148x outlier ratio**. Each value comes from 10 requests, and the run files hold no per-request TTFT. Thus the cause of the tail is not known.

**Production implication**: If you serve short prompts, your SLA must account for p99, not average. A model that "feels instant" (60ms median) can still have users waiting 8+ seconds in rare cases.

| Config | Prompt | Median | P99 | Tail Ratio |
|--------|--------|--------|-----|------------|
| unsloth (no spec) | 32 tok | 0.060s | **8.84s** | **148x** |
| nvidia (baseline) | 128 tok | 0.074s | 1.29s | 17.5x |
| nvidia (baseline) | 32 tok | 0.065s | 0.44s | 6.8x |
| nvidia (no PC) | 128 tok | 0.075s | 0.48s | 6.4x |
| unsloth+spec | 32 tok | 0.100s | 0.65s | 6.5x |
| nvidia (no PC) | 32 tok | 0.058s | 0.30s | 5.2x |
| RedHat | 8192 tok | 0.352s | 1.12s | 3.2x |
| nvidia (no PC) | 8192 tok | 1.167s | 1.20s | 1.03x |

Source: `latency` in `summary.json`. Tail Ratio is p99 / median.

**Note**: The RedHat run is consistent for short prompts (p95/avg ≈ 1.02x). At 8192 tokens and more, its median is a prefix-cache hit and its tail is a full prefill. The nvidia (baseline) run shows the same effect.

### 2. Prefill Throughput Plateaus at ~6,700 tok/s

For the values without prefix-cache hits, prefill throughput **plateaus around 6,700 tok/s at 2048+ tokens**. These are all runs up to 2048 tokens, and runs 2 and 4 at 8192 and 16384 tokens. `prefill_tps_avg` is prompt tokens / client TTFT, so it includes the network time and the first decode step. The run data does not show the cause of the plateau:

```
Prompt Length →  Throughput (all reliable models converge here)
32 tok         →     380-670 tok/s  (GPU overhead bound)
128 tok        →   1,100-1,690 tok/s  (warming up)
512 tok        →   3,100-4,000 tok/s
2048 tok       →   5,800-6,700 tok/s
8192 tok       →   6,800-7,000 tok/s  ← plateau
16384 tok      →   6,600-6,750 tok/s  ← ceiling
```

**Production implication**: For prompts under 512 tokens, expect 2-6x slower prefill. For production systems with mixed prompt lengths, your **average prefill throughput is dominated by short prompts**.

### 3. Decode Rate Is Stable Over Output Length (CV at Most 1.1%)

Across all 5 models and all 3 output lengths (512, 1024, 2048 tokens), the **coefficient of variation for decode speed is under 1.2%**. Every model produces tokens at a perfectly predictable rate:

```
Model                  Mean     Std Dev   CV
nvidia (baseline)      77.7     0.32      0.4%
nvidia no PC           79.0     0.86      1.1%
RedHat                 41.2     0.23      0.6%
unsloth (no spec)      74.9     0.11      0.2%
unsloth+spec           85.6     0.75      0.9%
```

**Limit**: Each run measured one request per output length. Thus the CV shows the spread over the three lengths, not the run-to-run variation.

### 4. TTFT is Negligible for Decode (Under 2% of Total Time)

In the unsloth + spec run, for 512+ output tokens, **TTFT contributes at most 2%** of total latency. The decode step dominates:

```
Output Length →  TTFT  Decode  TTFT%   Decode%
512 tokens     →  0.1s   6.0s    2%      98%
1024 tokens    →  0.1s  11.9s    1%      99%
2048 tokens    →  0.1s  24.2s    0%     100%
```

**Production implication**: For long outputs, the decode rate sets the total time. TTFT matters more for short completions and chat-style interactions.

### 5. Concurrency Scaling: Sub-Linear Latency, Super-Linear Throughput

In the three runs with 16 requests per level (runs 1, 2, and 4), at **16x concurrency**, average request latency grows only **2.2-2.6x** over single-request, while total throughput scales **6.0-7.3x**:

```
Level →  Latency Multiplier  Throughput Multiplier
  1 →       1.0x                  1.0x
  2 →       1.25-1.30x            1.54-1.60x  ← throughput exceeds latency!
  4 →       1.45-1.55x            2.58-2.76x
  8 →       1.68-2.02x            3.96-4.76x
 16 →       2.19-2.64x            6.04-7.30x
```

Source: `total_time_s.avg_s` and `aggregate_throughput_tok_s` in `concurrency`, `summary.json`. The **unsloth+spec** run is the fastest for single requests (2.50s avg, 102.2 tok/s at l1). Its levels 8 and 16 had at most 5 requests in flight, so they do not show its scaling. The nvidia baseline is the best for high-concurrency workloads (551.5 tok/s at l16).

### 6. Thinking Token Distribution: Right-Skewed, Not Bimodal

All models produce thinking tokens with **7-22% right skew** (avg/median ratio):

```
Model                  Avg    Median   Skew    Max    Max/Median
nvidia                 733    652      1.13x   986    1.51x
nvidia no PC           691    626      1.10x   986    1.58x
RedHat                 642    558      1.15x   981    1.76x
unsloth (no spec)      730    681      1.07x   982    1.44x
unsloth+spec           625    512      1.22x   986    1.93x
```

**Key insight**: The thinking token distribution is **slightly right-skewed, not bimodal**. There's no "thinking vs non-thinking" switch — instead, all models vary their reasoning depth smoothly from ~500 to ~1000 tokens. Only the unsloth + spec run (625 avg) used spec decoding. The 691 avg is from run 2, which had no spec decoding. Six prompts per run are too few to show a spec effect.

### 7. Meeting Basic: Systematic Zero Across ALL 5 Models

Every single run scored **0% on `meeting_basic`** (0/10 total tasks, not in the run files). This is either:
- A benchmark bug (the test is impossible or the rubric is wrong)
- A systematic failure in how Qwen3.6-A3B handles meeting-scheduling tool calls

This is worth investigating as a potential benchmark flaw before concluding it's a model limitation.

### 8. The "First Request Tax" in Concurrency

In runs 1 and 2, the **median TTFT is lower than the average TTFT** at levels 1 to 8. A few slow requests pull the average up. This is not true at all levels or in all runs. For example, at l16 of run 1, the avg TTFT is 0.633s and the median is 0.653s. The run data does not show the cause.

For example, nvidia (baseline) at l2: avg TTFT = 0.203s but median TTFT = 0.169s. All five runs sent one shared prompt to every concurrency request. In runs 1, 3, and 5, which had prefix caching on, some of these requests can be prefix-cache hits.
